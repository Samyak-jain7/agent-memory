An Architecture Study

Designing a ChatGPT-Style Memory System

A memory system is not a database. It is a standing decision about which pieces of information are valuable enough to carry into the future, and which ones the system is better off forgetting.

Built from a six-part design dialogue Lenses: design template, agentic-swe-kit, NPR 7150.2D Read top to bottom

How to read this. The pages that follow rebuild a single line of reasoning, from the first principle of why memory exists to a full implementation plan a principal engineer would actually defend. Each part opens with the question that drove it. The diagrams are the real architecture, redrawn. Nothing in the original discussion has been dropped.

Treat every section as a claim to interrogate, not a conclusion to memorize. Where would this break at ten million users? Which assumption is doing the quiet work? What would you have decided differently? Good. Write the question in the margin and keep going.

Part 0 / The Thinking Mindset

The lens before the system

Before any memory-specific design, three reusable instruments. A template for turning a messy workflow into components, a catalog of the ways agentic systems fail, and a spectrum for deciding how much human stays in the loop. Then the knowledge graph that ties domains together. These are not about memory yet. They are the way of seeing that the rest of the study uses.

How should I think about designing a ChatGPT-style memory system, step by step, without being limited to one framework? Explore industry standards too.

The opening inquiry
0.1

The Universal Design Template

After enough case studies, intuition becomes a repeatable process. Five steps turn any workflow, in any industry, into an agentic design.

Step 1. Map the mess

Document what actually happens today, not the process document nobody follows. Sit with the person doing the work and watch them.

What to write down
QuestionWhat to record
What triggers the work?Be specific. "Email arrives at claims@company.com with subject containing claim," not "claims come in."
What are all the steps in the middle?Every click, tab switch, copy-paste. Aim for ten to twenty. If you have five, you have not looked closely enough.
What comes out at the end?The actual deliverable: email sent, record updated, report generated, decision made.
Where is the human actually thinking?Mark each step MECHANICAL (reading, searching, copying, formatting) or JUDGMENT (deciding, evaluating, creating, advising).
How long does each step take?Clock it. Do not estimate, measure.
What breaks?Where errors happen, where it gets stuck, where the human says "this is annoying."

Step 2. Component assignment

Take each step from the mess map and assign it to one of the component types.

If the step involvesAssign it to
Detecting that work needs to happenTrigger
Fetching data from a system or databaseTool / API
Reading or extracting from unstructured inputLLM, or deterministic ML if structured
A score, classification, ranking, structured predictionDeterministic ML
Writing, drafting, summarising, explaining in languageLLM
Sending messages, updating records, creating filesTool / API
A judgment with legal, financial, or safety stakesHuman checkpoint

Most common mistakeAssigning an LLM to a step that should be deterministic ML. If the output must be the same every time given the same input, a score, a class, a ranking, it must be deterministic ML. If the output is language and some variation is acceptable, it can be an LLM.

Step 3. Design the connections

QuestionDesign decision
Which components can run at the same time?If A does not need B's output, run them in parallel.
Which must wait for another?If B needs A's output, run in sequence.
Where do results merge?Two parallel outputs that combine need a reconciler.
Where does the flow branch?Different inputs needing different handling need a conditional.
Where does memory matter?If feedback from one run should improve the next, design a memory store and a feedback loop.

Step 4. Failure mode analysis

ComponentIf it failsFallback
TriggerParser cannot extract the claim numberRoute to human with raw email
Tool / APIDatabase down, API times outQueue, retry in 5 minutes, alert if still down
Deterministic MLPredicts the wrong classConfidence threshold; below 70%, route to human
LLMHallucinates, wrong toneHuman review before it reaches the end user
ReconcilerParallel agents conflictFlag the conflict, route to human

Every component should fail gracefully. The system should degrade to slower but correct, never fast but wrong. The worst failure mode is a wrong answer delivered with confidence.

Step 5. Prototype scope

Choose what to build in thirty days. Not the whole system, the smallest version that proves the concept.

Scoping ruleHow to apply it
Highest-volume, simplest path firstAuto-approve cases (60% of volume, simplest logic), not fraud investigation (complex, 5%).
Measure against the manual baselineNot perfection. If the human misses 8% and you miss 5%, that is a win.
One metric that proves valueNot ten KPIs. "Time per claim dropped from 45 minutes to 2."
Run parallel, not replacementFor the first month both the human and the system process every item. Switch only when the system matches or beats human quality.
0.2

The Failure Modes Catalog

Every agentic system fails. The only question is whether it fails safely. Seven recurring modes, and how to design against each.

1. LLM hallucination in a critical path

The model generates something that sounds right but is factually wrong: a legal summary citing a clause that does not exist, a brief attributing experience a candidate never had. It happens because LLMs produce the most probable next token, not the most accurate one.

  • Citation requirement. Every factual claim links to a source document, page, or record. If it cannot be cited, it should not be said.
  • Fact-checking layer. A verification step checks key claims against source data after generation.
  • Human review for high stakes. Nothing LLM-generated reaches a client, patient, or regulator unreviewed.
  • Prompt design. Instruct the model to say "I could not find information about X" rather than guess. Explicit uncertainty beats confident hallucination.

2. ML model drift

The model was accurate at deployment and degrades as the world changes. A fraud scorer trained on 2024 data misses 2025 patterns. Defend with a monitoring dashboard, alert thresholds, a periodic retraining schedule, and a fallback to rules while retraining.

3. Tool / API timeout

An external system does not respond and the pipeline stalls. Defend with timeout-and-retry, graceful degradation on partial data, queue-and-process-later, and a circuit breaker that stops calling a dead service.

4. Feedback loop poisoning

Bad feedback gets stored and degrades future behavior. A recruiter system "learns" a preference for male candidates from two unrepresentative shortlists. Defend with a minimum sample size, a feature audit for protected proxies, decay on old feedback, and a human override that can inspect and reset memory.

5. Orchestration deadlock

Two parallel agents wait on each other, or a reconciler never receives an output. Defend with timeouts on every step, health checks, idempotent operations, and a dead letter queue for undeliverable messages.

6. Human bottleneck

Auto-handling works, but the escalation queue grows faster than humans can clear it. Defend with escalation-rate monitoring, queue prioritisation by urgency and value, threshold adjustment under load, and honest capacity planning before deployment.

7. The "almost right" problem

Output that is 90% correct and 10% wrong in ways that are hard to spot, while reviewers drift into automation complacency. Defend by varying and rotating reviewers, flagging low-confidence outputs, running random audits, and injecting known-wrong inputs to test whether reviewers still catch them.

0.3

The Human-in-the-Loop Spectrum

Not every system needs the same level of human involvement. The right level is a design choice, not a default.

LevelDescriptionWhere it fits
Full automationSystem handles everything; human samples periodically.Routine reorders, simple status inquiries
Human reviews outputSystem produces, human verifies before it goes out.Legal summaries, marketing options
Human handles exceptionsSystem auto-handles easy cases, human sees the hard ones.Escalated claims, negative sentiment, anomalies
Human decides, system preparesSystem gathers all context, human makes the call.Doctor reads a pre-built profile, broker reviews a shortlist
Full human with AI assistHuman does the work, system helps at specific steps.Early-stage recruiting, heavily edited creative

The right level depends on three factors. Consequence of error: a wrong support reply is annoying, a wrong medical triage is dangerous. Reversibility: an auto-approved claim can be reviewed later, a medical procedure cannot be undone. System maturity: new systems need more oversight; proven ones can run with less.

Start with more human involvement than you think you need. Reduce it as the system proves itself. It is far easier to remove a checkpoint than to recover from removing it too early.

Part I / First Principles

Why memory exists, before how it works

Most people ask how to build a memory system. The better question is why a memory system exists at all, because once you can answer that, the architecture becomes almost obvious. This part climbs from that first principle to a full memory architecture in eleven levels.

Read it twice. The first time for the memory system. The second time for the method, because the real lesson is the order of questions a strong engineer asks when handed any system they have never seen before. That is what survives an interview and what generalizes to the next design.

How each level worksEvery level ends with two things. The question we ask is the reusable thinking move, the one you could apply to a search system, a payments ledger, or a recommendation engine. Carry into the architecture is the concrete piece we keep: a component, a field, a rule. By the end of the study those pieces assemble into one design. We are not just learning. We are building.

How do I design ChatGPT's kind of memory system? What should my step-by-step thinking procedure be?

The driving question
L0

First Principles

Imagine ChatGPT without memory. In one conversation you say you like short answers. In the next you ask it to help plan your startup, and it has forgotten everything. The system pays the same cost again: the user re-establishes who they are, what they want, and how they like to be spoken to. So memory exists to solve exactly one problem: reducing information loss across interactions.

That single sentence gives the first design principle, and it already rules out the most common mistake, which is treating memory as a place to dump everything the user ever said.

Memory is not storage. A database stores everything. A memory system stores only the things that improve future behavior. Memory is selective retention of information that improves future decisions.

Hold onto the word selective. It means the very first thing standing in front of our store is not a write, it is a decision about whether to write at all. That gate is the seed of the whole architecture.

The question we ask

Why does this system exist at all, and what single problem justifies it?

Generalizes to: before any component, name the one cost or loss the system removes. If you cannot, you are designing a feature nobody needs.

Carry into the architecture

A write gate. Storage is never the first step. Every candidate memory passes a selection decision first. We will give this gate a name in Level 5 (the evaluator) but it is born here, as a principle: store only what improves a future decision.

L1

Start From Human Memory

Before touching vectors, embeddings, databases, or RAG, ask how human memory works. This is a deliberate move. When you are designing something genuinely hard, look for a system that already solved it. Human memory has been refined for a very long time, and the engineering vocabulary we need turns out to be sitting inside cognitive science.

The key observation is that humans do not remember everything, and the things they keep are not stored the same way. They remember in kinds, and each kind behaves differently: different lifetime, different update rules, different retrieval triggers. That difference is the gift, because it tells us our store should not be one undifferentiated bucket.

Episodic memory / experiences, time-stamped events
The user launched a startup. The user traveled to Kashmir. These are things that happened, with a when attached.
Semantic memory / stable facts, no timestamp needed
The user knows Python. The user works in ML. True across many conversations, rarely changing.
Procedural memory / how the user likes things done
The user prefers bottom-up learning. The user likes first-principles explanations. This shapes how we respond, not what we say.
Working memory / the live context, tiny and volatile
Everything inside the current conversation. Held for minutes, then gone unless promoted to a longer-lived kind.

Read those four again as an engineer. Episodic memory wants an event log with timestamps. Semantic memory wants a fact table you can overwrite when a fact changes. Procedural memory wants a small, high-priority preference set that is almost always worth loading. Working memory is just the context window. The taxonomy is not trivia, it is a schema waiting to be written.

Notice what this implies: ChatGPT memory is basically an engineering version of cognitive science. The promotion path matters too. A fact mentioned once in working memory, if it proves useful, gets promoted to semantic or procedural memory so it survives the conversation. That promotion is exactly the write gate from Level 0, now with a direction.

The question we ask

Is there a mature system, natural or engineered, that already solved a version of this problem, and what structure can I borrow from it?

Generalizes to: analogies are not decoration, they hand you a ready-made decomposition. Caches borrow from working memory; ledgers borrow from accounting; recommendation borrows from word of mouth.

Carry into the architecture

A typed memory taxonomy. Our store is not one table. It is partitioned by kind, and the kind drives the rules:

  • episodic events with timestamps, append-only
  • semantic facts, overwritable, deduplicated
  • procedural preferences, small set, high retrieval priority
  • working the live context window, not persisted by default
L2

Define the Job of Memory

Now apply the template. Map the mess. Without memory, the same costs repeat on every conversation.

EventProblem
User repeats a preferenceWaste
User repeats goalsWaste
User repeats project contextWaste
User repeats constraintsWaste

The trigger is a new conversation starting. The output is relevant historical context appearing. The human thinking required is none. The work is entirely mechanical, which is exactly what makes it automatable.

Component assignment. Break memory into parts. A trigger fires when a message arrives. An extraction agent (an LLM task) reads the conversation and finds preferences, goals, projects, relationships, and long-term facts. A memory classifier decides whether something is worth remembering, because not all information matters: remember that the user is building SecondBrainLabs, do not remember that the user ate dosa today. The memory store is a database. A retrieval agent searches relevant memories when a conversation starts. A context composer assembles the package, and the response generator uses it.

So what exactly does the job produce? When the extractor reads a message and the classifier approves it, the thing that lands in the store is a structured record, not a blob of text. Deciding its fields now is what lets every later component (ranking, decay, governance, explainability) do its work. A first cut of that record:

memory {
  id            unique identifier
  user_id       owner, isolates one user from another
  type          episodic | semantic | procedural
  content       the fact, in plain language
  importance    how much this should weigh        (set at write)
  confidence    how sure we are it is true         (set at write)
  source        where it came from: conversation id, document, user
  created_at    when we learned it
  updated_at    when it last changed
}

Two fields are quietly doing strategic work. importance and confidence are what let the system distinguish "the user is building SecondBrainLabs" from "the user is maybe thinking about moving cities." source is what lets the system later answer the question why do you think that. We are not adding fields for completeness, each one earns its place by enabling a future decision.

The question we ask

What are the components, what flows between them, and what is the shape of the data each one hands to the next?

Generalizes to: a system is components plus the contract between them. Name the boxes, then name the object that travels the arrows. The object is usually more important than the boxes.

Carry into the architecture

The component pipeline and the memory record.

  • Write path: Trigger → Extractor → Classifier → Store
  • Read path: Retriever → Context Composer → Response LLM
  • The record schema above, with importance, confidence and source as load-bearing fields
L3

Industry-Standard Thinking

Most beginners picture one arrow: user, to vector database, to retrieve. That is not how production systems work, and the gap between those two pictures is the gap between a demo and a product. A modern memory system is six separate subsystems, each with its own job, its own failure modes, and ideally its own owner.

The six-subsystem framework
SubsystemIts one jobThe question it answers
CaptureTurn raw conversation into candidate memoriesWhat did the user just reveal?
StoragePersist memories durably and by typeWhere does this live and how is it indexed?
RetrievalFind the memories relevant to the momentGiven this query, what matters?
EvaluationDecide what is worth keeping and how good retrieval wasIs this useful, and is it working?
DecayLet unused memories fade and archiveWhat should be forgotten?
GovernanceControl what may be remembered, deleted, inspectedWhat are we allowed to keep, and can the user see it?

This is the framework, and it is the one to reach for in an interview. When someone says "design a memory system," you do not start naming databases. You name these six boxes, say which one is hardest (almost always retrieval and evaluation), and then go deep where it counts. Collapsing all six into "a vector store" is the single most common mistake, because it hides four of the six problems.

The question we ask

What does the mature, production version of this decompose into, beyond the happy path the demo shows?

Generalizes to: every interesting system has a hidden back half. Storage and retrieval are visible; evaluation, decay, and governance are where production lives. List them before you are asked.

Carry into the architecture

Six subsystems as the top-level decomposition. The final architecture will have exactly these boundaries: Capture, Storage, Retrieval, Evaluation, Decay, Governance. Every component we add later will slot into one of them.

L4

Memory Architecture: Four Layers

The taxonomy from Level 1 was by kind. This layer is by lifetime, and the two are complementary: kind tells us how to store a memory, lifetime tells us where and for how long. Production systems keep these four layers distinct rather than dumping everything into one table, because each has a different read frequency and a different cost.

LayerLifetimeHoldsWhere it lives
Working memoryMinutesThe current conversationContext window
Session memoryDays to weeksThe current project: SBL, the ML course, the Agentic SWE KitFast cache, e.g. Redis
Long-term memoryMonths to yearsThe user prefers first-principles learning, runs a startup, likes detailDurable store, Postgres
Knowledge memoryReferenceExternal, non-personal documents: PDFs, course materials, papersVector index, RAG

The layering also gives a routing rule for writes. A new fact enters working memory for free. If it proves useful within the session, it is promoted to session memory. If it recurs across sessions, it graduates to long-term memory. Uploaded documents skip the personal layers entirely and go to knowledge memory. Promotion is selective retention in motion, which is the Level 0 principle expressed as data flow.

The question we ask

What are the natural lifetimes of this data, and should things that live for minutes really sit in the same store as things that live for years?

Generalizes to: lifetime is a first-class design axis. Mixing hot, short-lived data with cold, long-lived data in one store is how systems get slow and expensive at once.

Carry into the architecture

Four storage tiers plus a promotion rule. Working in the context window, session in a cache, long-term in Postgres, knowledge in a vector index. Writes flow upward by usefulness: working → session → long-term, with documents routed straight to knowledge.

L5

The Most Important Question: When to Write

This is where most memory systems fail. The naive system stores everything, which creates memory pollution: a store so full of noise that retrieval drowns and every context is cluttered with irrelevant facts. The write gate we seeded in Level 0 now gets a job description. Instead of storing by default, score each candidate by future utility, asking one question: will this improve a future conversation?

"I use PostgreSQL" / utility high
A stable fact that will shape future technical answers. Store it.
"I am building SecondBrainLabs" / utility high
A project that anchors many future conversations. Store it, high importance.
"Today I had coffee" / utility low
True, but it changes no future decision. Discard it.

This is the component that Level 0 promised. Call it the evaluator. In an MVP it can be an LLM judge prompted with should this memory improve future conversations, yes or no, importance one to ten. At scale it becomes a cheap deterministic classifier. Either way it sets the importance and confidence fields from the Level 2 record, which is why those fields existed before we had the component to fill them.

A good memory system is mostly a forgetting system. The hard engineering is not in what you keep, it is in what you have the discipline to throw away.

The question we ask

What is the cost of keeping this versus the value, and what is the rule that decides at write time?

Generalizes to: any system that accumulates state needs an admission policy. Logs, caches, indexes, memories. Decide what gets in before you decide where it goes.

Carry into the architecture

The Evaluator, sitting between Extractor and Store. It scores future utility, sets importance and confidence, and drops low-value candidates. This is the named write gate, and it belongs to the Evaluation subsystem from Level 3.

L6

Retrieval Design

Another common mistake: people optimize storage, professionals optimize retrieval. Storage is mostly solved. Retrieval is where the system feels smart or feels broken, because the user only ever experiences what you surface, never what you kept. When the user says "help me design a course," not all memories matter, and pulling the wrong ones is as bad as pulling none.

Work the example. The query is help me design a course. The store holds dozens of memories. Which ones belong in context?

MemoryWhy it scores high or low
User prefers first-principles teachingHigh. Procedural, directly shapes the answer.
User's students are ML beginnersHigh. Defines the audience for the course.
User is running an ML course projectHigh. Same project, recent, reinforced.
User uses PostgreSQLLow. True, but irrelevant to course design.
User traveled to KashmirLow. Episodic, no bearing on the task.

To make that judgment automatically you score every candidate across several signals, then take the top-k.

  • Semantic similarity. Embedding match between query and memory.
  • Recency. Newer memories weigh more.
  • Frequency. Mentioned repeatedly, so likely durable.
  • User importance. Explicitly saved or rated high by the evaluator.
  • Project relevance. Belongs to the active project.
Final Score = 0.4 Semantic
            + 0.2 Recency
            + 0.2 Frequency
            + 0.2 Importance

then retrieve top-k

One more point that separates a robust system from a fragile one. Pure embedding search misses exact facts (a name, a version number, a price), so production retrieval is hybrid: vector search for meaning, keyword search for exact strings, and a graph link for related entities. The ranking formula then fuses them. This is the fix for the retrieval-miss failure we will see in Level 8.

The question we ask

Given a specific request, which subset of everything we know actually matters, and how do we rank it so the best rises to the top?

Generalizes to: relevance is a scoring problem, not a lookup. Name your signals, weight them, and make the weights tunable. Search, feeds, and recommendation are all this same move.

Carry into the architecture

A Ranking service and hybrid retrieval. Retrieval fans out across vector, keyword, and graph, then a ranking step fuses signals with tunable weights and returns top-k. This is the heart of the Retrieval subsystem.

L7

Memory Decay

Human memory fades, and the system should too, for the same reason: a memory that never gets used is a memory that is probably no longer true or no longer relevant. Each memory carries a weight that erodes over time unless something reinforces it.

weight = importance
       x recency
       x reinforcement

Reinforcement is the interesting term. Every time a memory is retrieved and actually helps, its weight is topped up, which means useful memories stay alive and stale ones sink on their own. A user mentioned wanting to learn Kubernetes eighteen months ago and never again. The weight decays, and eventually the memory is archived rather than surfaced into every context. Archived, not deleted, because the user might still ask about it, and provenance must survive.

Mechanically this is a background job, not something that runs on the request path. Nightly, multiply weights by a decay factor, archive anything below a floor. This keeps the store from exploding and keeps retrieval fast, which connects directly to the economics we will reach in Part III.

The question we ask

What should happen to this piece of state over time if nothing ever touches it again?

Generalizes to: state without a decay or expiry policy grows without bound. Caches, sessions, feature flags, memories. Design the forgetting at the same time as the remembering.

Carry into the architecture

A background decay job and two more fields. Add weight and reinforcement_count to the record. A nightly worker decays weights and archives below a floor. This is the entire Decay subsystem, off the request path.

L8

Failure Mode Analysis

Apply the failure template directly to memory.

FailureWhat happensFix
Memory pollutionStores everything, context overloadUtility classifier
Wrong memory"Thinking of moving to Bangalore" stored as "lives in Bangalore"Confidence scores, verification
Retrieval missMemory exists but is never retrievedHybrid retrieval: vector, keyword, graph
Feedback poisoningSystem learns a bad preferenceMinimum evidence threshold
Memory explosionMillions of memoriesHierarchy, archive, summarization, compression

Notice that each fix is a component we have either already carried or will add: the utility classifier is the evaluator, confidence scores are a record field, hybrid retrieval is the ranking service, the minimum evidence threshold guards the evaluator, and hierarchy plus archival is decay plus summarization. Failure analysis did not invent new parts, it justified the parts we chose.

The question we ask

For each component, what happens when it fails, and does the system degrade to slower-but-correct rather than fast-but-wrong?

Generalizes to: run a pre-mortem before code. Walk each box and break it on purpose. The fallbacks you design now are the incidents you avoid later.

Carry into the architecture

Five safeguards baked into existing components. Utility classifier on write, confidence and verification on the record, hybrid retrieval against misses, minimum-evidence threshold against poisoning, and archival plus summarization against explosion. No new boxes, just hardened ones.

L9

A ChatGPT-Level Architecture

This is the first time the carried pieces snap together. Everything in the diagram below was earned in an earlier level: the extractor and classifier from L2, the evaluator and its utility score from L5, the typed long-term store from L1 and L4, the retrieval engine and ranking from L6. A write path that extracts, evaluates, and stores. A typed long-term store. A read path that retrieves, composes context, and answers. This is not yet the full production architecture (Parts II and III add the stack, scale, and safeguards) but it is a complete, defensible core.

The question we ask

Can I now assemble the pieces into one coherent flow, and does every box trace back to a decision I can defend?

Generalizes to: assembly is a test. If a component cannot be traced to an earlier why, it is either missing a justification or it does not belong.

Carry into the architecture

The core memory architecture. Write path, typed long-term store, read path. Parts II to VII will wrap this core in a real stack, production concerns, and an implementation plan, but the spine is now fixed.

L10

The Mental Model

Whenever designing any memory system, ask these ten questions in order.

  1. What decision will this memory improve?
  2. What information deserves remembering?

Now, and only now, the technology

2.3

What Production Adds Later

Past the MVP, memory becomes much more sophisticated. These are the components a large system grows into, reserved deliberately for version two. Each one sounds like jargon until you see the plain idea and the example behind it.

Memory graph

In plain terms: instead of keeping memories as a flat list of sentences, you store them as things (nodes) joined by relationships (edges). The very first edge is usually the user linked to their own project, and that single link is the seed of the whole graph.

Example. A node for the user connects to a node for SecondBrainLabs by "founds," to a node for the ML course by "teaches," and to a node for students by "audience." Now when the user asks about SBL pricing, the system can walk user, to startup, to pricing, instead of hoping a fuzzy text match lands. Relationships you can follow are often more reliable than similarity you have to guess.

Into the architectureA graph store sits beside the vector store. For an MVP it is just an edges table in Postgres (from_id, to_id, relation). Retrieval gains a third path that walks the graph.

Hybrid retrieval

In plain terms: search three ways at once because each method catches what the others miss. Vector search finds meaning, keyword search finds exact strings like a name or a version number, and graph search finds related things.

Example. The query "what database does the user use" with all three: vector surfaces "prefers relational databases," keyword nails the literal "pgvector," graph follows user, to project, to tech stack. Three weak signals combine into one strong answer.

Into the architectureThe Retriever fans out to vector, keyword, and graph in parallel, and the Ranking service merges their scores. This is the full version of the Level 6 idea.

Reflection agent

In plain terms: a background worker that occasionally re-reads many raw memories and rewrites them into fewer, cleaner ones. It is the system tidying its own notes.

Example. Three scattered memories, "uses Postgres," "uses pgvector," "deploys with Docker," get consolidated into one higher-level memory: "the user runs a Postgres and Docker stack." Less clutter, better retrieval.

Into the architectureA scheduled agent reads the store, writes consolidated memories back, and records what it learned in learning memory. It runs off the request path, like decay.

Memory compression

In plain terms: replace a hundred detailed memories with ten summaries, to save storage and, more importantly, to save room in the model's context window. Reflection improves quality; compression reduces volume and cost.

Example. Fifty small facts about the user's course become a single paragraph profile. The originals are archived, the summary is what gets loaded into most conversations.

Into the architectureA background step produces summaries with higher retrieval priority and archives the raw rows. This is the direct fix for the memory-explosion failure from Level 8.

Conflict resolution

In plain terms: when a new memory contradicts an old one, decide which is true now. The system must not simply keep both and confuse itself.

Example. Old memory says "works in EdTech," new memory says "runs a B2B SaaS." Three possibilities: it is a real change (update, old one archived), both are true (keep both), or one is a mistake (keep the higher-confidence one). A simple rule: newer and higher-confidence usually wins, but always keep the old one's provenance so the change is auditable.

Into the architectureA check on the write path (or inside reflection) compares each new memory against existing ones on the same subject before committing.

Memory governance

In plain terms: the rules for what may be remembered and what must be forgotten. This grows into a full concern in Part III, but it starts here as a policy that wraps every write.

Carry into the architecture

A v2 shelf. Graph store, reflection agent, compression, and conflict resolution are drawn as dashed, deferred components, so the architecture shows the growth path without over-building today.

2.4

The Five Subsystems, Restated

The biggest shift is realizing what kind of thing you are building.

A memory system is not Postgres plus embeddings. It is a continuously learning information management system, and it has five verbs.

Capture     Store     Retrieve     Update     Forget

Design those five well and the technology choices become straightforward. Design them poorly and the best vector database in the world will not save the system. Note that this restates the six subsystems from Level 3 as actions: governance is the policy that wraps all five.

Part III / Production Engineering

Making it work for millions, not for one

Most memory tutorials stop at "how do I make memory work." The harder question is "how do I make memory work in production for millions of users," and those are different design problems. The production lifecycle from Part 0 supplies the missing lenses: observability, security, reliability, infrastructure, governance, economics, and learning.

The agentic kit also talks about scalability, reliability, latency, cost, economics, governance, infrastructure. Where does memory meet those?

Raising the production bar
3.1

The Phases Production Cannot Skip

Beginners design capture, store, retrieve. Senior engineers add scale, observe, secure, govern, recover, optimize. The second system is the one that survives.

Phase 0 / Cognitive design

Before technology, ask what decisions memory will improve. If memory is not improving a future decision, do not build it.

SystemWhy memory exists

Phase 10 / Observability

In plain terms: can you see what the system is doing while it runs? A memory system without it is a disaster, because when memory goes wrong users lose trust instantly and you find out from complaints instead of dashboards. You measure four things: is memory helping (retrieval rate, retrieved over stored), is it accurate (correction rate, counted from "that's wrong"), how fast (retrieval latency, target under 100ms), and how expensive (dollars per write and per retrieval).

How you build it. Every component emits two kinds of signal: a metric (a number, like latency) and a trace (the path one request took through the layers). Prometheus collects the numbers, Grafana draws the dashboards, PostHog tracks product events like "user corrected a memory," and an LLM-tracing tool such as Langfuse or OpenTelemetry records each extraction and retrieval so you can replay exactly what happened. Example: a Grafana panel shows retrieval latency spiking to 400ms at 9am, the trace points at the embedding service, and you scale it before users notice.

Phase 11 / Security

In plain terms: keeping one user's memories away from every other user, and keeping dangerous data out of the store entirely. Most memory systems are really security systems wearing a friendly face. Return user A's memory to user B once and it is game over.

How you build it. Three defenses, none optional. Tenant isolation: every query carries WHERE user_id = ..., enforced at the database with Postgres row-level security so a forgotten filter cannot leak data. Encryption at rest: sensitive memory is encrypted (AES-256) with keys held in a key manager such as AWS KMS or HashiCorp Vault, so a stolen disk is useless. PII detection: a filter such as Microsoft Presidio scans every candidate memory and blocks passwords, card numbers, and secrets before they are ever written. Example: the user pastes an API key mid-conversation; the PII filter catches it and the evaluator drops it, so it never reaches the store.

Phase 12 / Reliability

In plain terms: when a part breaks, does the whole thing fall over, or does it limp along correctly? The defining test: what happens when the memory database is down? A bad system takes the whole chatbot down with it. A good system disables memory and keeps chatting, just without personalization. Graceful degradation, always. You build it with timeouts (give up after, say, 200ms), a circuit breaker (stop calling a dead service for a minute), and a fallback path that answers without memory.

Phase 13 / Infrastructure

In plain terms: infrastructure is the machinery your code actually runs on, the servers, databases, queues, caches, and the network between them. For a hundred users one box running Postgres is enough. For a million, the single service splits into a gateway (the front door that routes requests) and separate memory, retrieval, embedding, and storage services that each scale on their own.

How you build it. Each service runs in a Docker container so it ships the same everywhere; Kubernetes runs many copies and restarts any that crash; a load balancer spreads traffic; a message queue (SQS, Kafka) carries write jobs so a slow extractor never blocks the chat; and Redis caches hot session memory. Example: at 9am traffic triples, Kubernetes spins up four more retrieval containers, and the queue absorbs the write spike so users still get instant answers.

Phase 15 / Governance

In plain terms: governance is the rulebook for what the system is allowed to remember, who can change or delete it, and whether the user can see why it knows what it knows. Three questions. What can be remembered: preferences yes, passwords no, medical history maybe, it depends on consent and law. Who can delete: the user always, an admin for support, the system on a schedule. Explainability: when the user asks "why do you think I like first-principles explanations," the system answers "based on conversations 42, 56, 61."

How you build it. An append-only audit log records every write, read, and delete; a consent flag on each user controls what categories may be stored; data-residency rules keep an EU user's memories on EU servers (a real legal requirement under GDPR). Auditability is a feature, not an afterthought, and it is exactly why the record carried a source field since Level 2.

Phase 16 / Economics

In plain terms: at scale, the bill, not the code, becomes the constraint. At ten million users with a hundred memories each, that is a billion memories. Storage stays cheap, but embedding, retrieval, and stuffing memories into the model's context get expensive fast.

A rough example. Embedding one memory costs a fraction of a cent, say $0.00002. A billion of them is around $20,000 just to embed once, and you re-embed when models change. Worse, every retrieval that injects ten memories into a prompt adds tokens to every single message, which at scale dwarfs storage. So the questions become: should every memory be embedded (maybe not), retrieved (no), injected into context (definitely not). Senior engineers optimize cost per useful memory, not total memories stored. The lever is selectivity: the write gate and decay from Part I are also cost controls.

Phase 18 / CI/CD

In plain terms: CI/CD is the automated safety net that tests and ships your code, so a change cannot quietly break memory in production. Continuous integration runs tests on every change; continuous delivery deploys only what passes.

Example. A retrieval regression test stored as a fixed case: input "user asks about ML course," expected "teaching-preference memory retrieved." A new prompt improves extraction but accidentally breaks ranking; the test fails and the build is blocked before users ever see it. For AI specifically you add an eval gate (the new version must score at least as well as the old on a golden set) and shadow mode (run the new version silently next to the old and compare) before switching traffic over.

Phase 19 / Human-in-the-loop

Particularly important for memory. When the system says "you live in Bangalore" and the user says "no, I moved," that correction must flow back as a memory update. And explicit controls matter: "forget that" should actually remove the memory.

Phase 20 / Continuous learning

The hardest phase, where memory systems become knowledge systems. Reflection compresses a hundred memories into "the user is an ML educator." Conflict resolution reconciles old ("works in EdTech") against new ("runs B2B SaaS"): both true, one obsolete, or a genuine change?

The question we ask

What breaks, leaks, or bankrupts us when this succeeds and the load multiplies by ten thousand?

Generalizes to: design for the success case, not just the demo case. Isolation, degradation, cost-per-unit, and auditability are architectural, decided early or regretted late.

Carry into the architecture
  • Observability plane: retrieval rate, correction rate, latency, cost.
  • Security plane: tenant isolation on every query, encryption at rest, PII filter on write.
  • Reliability: memory retrieval is optional; failure degrades to an answer without memory.
  • Scaled topology: gateway plus independent memory, retrieval, embedding, write services.
  • Governance plane: deletion controls and explainability from the source field.
3.2

Architecture Determines Stack

If you applied this thinking, the design document would not open with Postgres, pgvector, OpenAI embeddings. It would open with the questions that decide the shape: what happens if retrieval fails, what happens at ten million users, can one user's memory leak, what is the cost per retrieval, can users inspect and delete, how do we know memory helps, how does memory evolve. Only after answering those do you reach for the stack.

Technology choices are implementation details. Scalability, reliability, economics, governance, and observability are architectural decisions. The architecture should determine the stack, not the other way around.

Part IV / The Senior Engineer's Lenses

What separates a good design doc from a principal's

Scalability, reliability, security, observability, cost, governance are table stakes. The things senior engineers spend even more time on come before those: the trade-offs, the invariants, the lifecycle, and the question of whether the feature should exist at all.

Is there anything I'm missing on how senior engineers would design the whole system, or is that it?

Pushing past the obvious
4.1

Twelve Lenses Most Designs Miss

1 / Trade-offs

In plain terms: every choice buys you something and makes you pay for something else, and the skill is naming both. A junior asks "Postgres or Pinecone." A senior asks "what trade-off are we making." Every decision is a gain paid for by a cost.

DecisionGainCost
Store all memoriesBetter recallHigher retrieval cost
Store fewer memoriesLower costMore forgetting
Human reviewBetter accuracyMore latency
Full automationLower costHigher risk

2 / Invariants

In plain terms: invariants are rules the system must never break, no matter what else changes. Most docs describe what the system does. Great ones describe what it must never violate, and those rules outrank any technology choice.

  • User A's memory must never be returned to user B.
  • Deleted memories must never be retrieved.
  • Memory retrieval failure must not prevent response generation.
  • Every stored memory must have provenance: conversation, document, or human input.

3 / Capacity planning

In plain terms: doing the arithmetic of success before it arrives, so you are not surprised by your own growth. Model the jump from a hundred to a million users before writing code.

Worked example. Say each active user writes 5 memories an hour and you have a million users, 10% active at once. That is 100,000 users times 5, so about 140 memory writes per second, plus a retrieval on most messages. Each write needs one embedding call, so roughly 12 million embeddings a day, and at a hundred memories per user the store grows by tens of gigabytes a month. Now you know to put writes on a queue and to budget for embeddings, before a single line of code locks you in.

4 / Data lifecycle

In plain terms: a memory is not just stored, it has a whole life, and you must design every stage. It is born, lives, changes, and dies: creation (who made it), update (can it change), merge (what if two conflict), archive (when inactive), delete (when gone).

Example. "User is exploring a move to Bangalore" is created with low confidence. Weeks later "User now lives in Bangalore" arrives; the two are merged, confidence rises, the old wording is archived but kept for provenance. A year later the user says "forget where I live," and it is deleted for good. One fact, five stages. Designing this is more important than the database itself.

5 / Domain boundaries

Do not design "a memory system." Design a memory service, a retrieval service, an embedding service, a profile service, a feedback service. Separate responsibilities, or everything becomes coupled.

6 / Operational reality

In plain terms: design for the day things are broken, because in production they will be. Most designs assume the system works. Real life serves you a database down, Redis down, the LLM provider having an outage, the embedding model silently changing its output, a bad deployment at 2am. Example: the embedding provider ships a new model version with different vectors, so old and new memories no longer compare correctly; if you planned for it, you pinned the model version and re-embed on a schedule instead of waking up to garbage retrieval.

7 / SLOs and SLAs

In plain terms: an SLO is the target you hold yourself to; an SLA is the same promise made to a customer with consequences if you break it. Write them down or design arguments stay subjective. For memory: availability 99.9% (down at most about 43 minutes a month), retrieval latency p95 under 100ms (95 out of 100 retrievals finish in under a tenth of a second), and precision 90% (nine of every ten retrieved memories are actually relevant). The "p95" habit matters because averages hide the slow requests that users actually feel.

8 / Evaluation framework

In plain terms: how do you know the memory is any good, with numbers instead of vibes? Most AI systems fail because nobody answered this. You build a golden set: fifty real queries, each labelled with the memories that should be retrieved. Then you measure precision (of what we retrieved, how much was relevant) and recall (of what was relevant, how much we found), score memory correctness with an LLM-as-judge, and track the correction rate from real users.

Tools. Frameworks like RAGAS, promptfoo, or Langfuse run these evaluations automatically on every change, so retrieval quality becomes a number on a dashboard, not a hope. Design the evaluation before deployment, never after.

9 / Migration strategy

V1 memory has preference, goal, project. Six months later it also has relationship, constraint, expertise. How do old memories migrate to the new schema? This gets serious at scale.

10 / Organizational design

Who owns this system: AI team, platform, infra, data? Many systems fail because ownership is unclear.

11 / Product thinking

Should this feature exist at all? If memory raises answer quality 2% but doubles cost, maybe do not build it. The best architecture is often deleting a feature.

12 / The meta layer: why

The highest level. Why does this system exist, what business metric changes, what user behavior changes, what decision improves? If you cannot answer those, stop designing.

The question we ask

What must this system never do, what are we trading away, and should it exist at all?

Generalizes to: invariants, trade-offs, and the meta-why are the principal-engineer toolkit. They apply to every system, and they are what an interviewer is really probing for.

Carry into the architecture
  • Four invariants printed on the architecture as hard constraints.
  • Service boundaries: memory, retrieval, embedding, profile, feedback.
  • An SLO band: 99.9% availability, p95 under 100ms, 90% precision.
  • A lifecycle annotation on the record: create, update, merge, archive, delete.

Part V / Decisions Under Uncertainty

The last fifteen percent is judgment, not architecture

From a systems-thinking view the design is now 85 to 90% complete. The remainder is decision-making under uncertainty, which is what principal engineers actually spend most of their time on: surfacing assumptions, naming risks, recording decisions, and planning the exit.

Anything else we're missing, or are we good? And which software should I use to design the architecture?

Closing the design loop
5.1

Five Instruments of Judgment

1 / Assumptions register

Every design hides assumptions, and when systems fail it is usually an assumption that failed. Write them down: users create under 100 memories per month, retrieval latency stays under 100ms, users rarely change preferences. Now they are testable instead of invisible.

2 / Risks register

Different from failure modes. A failure mode is "the database goes down." A risk is "users don't trust memory enough to enable it," or "memory quality is too low to justify the cost." Architecture is not just technical risk, it is product risk.

3 / Architecture Decision Records

Document every major decision so that six months later you remember why.

ADR-001
Decision      Use PostgreSQL + pgvector
Alternatives  Pinecone, Weaviate
Why           Lower operational complexity, existing team expertise
Trade-offs    Less specialized vector search

4 / Exit strategy

The most senior question: if this becomes the wrong architecture, how do we leave? Today Postgres plus pgvector, future a dedicated retrieval cluster. Can you migrate? Always design escape hatches.

5 / Conway's law

Systems mirror the communication structure of the organization that builds them. One engineer, a monolith is often correct. Ten teams, services may be necessary. Many engineers over-engineer because they design for Google while operating as a startup.

The question we ask

Which of my beliefs are unproven, what would make this the wrong design, and how would I back out if it were?

Generalizes to: mature design is honest about uncertainty. Assumptions, risks, decision records, and exit hatches travel to every project and every interview whiteboard.

Carry into the architecture
  • An assumptions register and a risks register attached to the doc.
  • An ADR log, opened with the Postgres-plus-pgvector decision.
  • An exit hatch: storage abstracted so the vector layer can move to a dedicated cluster.

Part VI / From Artifacts to Decision Loops

The real source of truth is not the code

There is a subtle shift in how the most advanced teams work. They think slightly less in artifacts and more in decision loops. A senior engineer does not think requirements then architecture then code. They think decision, implementation, observation, feedback, updated decision, repeated forever.

How would a senior engineer actually implement this memory system, end to end?

From design to build
6.1

From Artifacts to Loops

The naive pipeline is linear: requirements, architecture, coding plan, code. The real one is a loop, and the loop never stops.

This reframes what the source of truth is. Most people think the codebase is the truth. It is not. The truth is the decision base: the why, the trade-offs, the constraints, the assumptions, the rejected alternatives, the failure modes, the lessons learned. That is exactly what the assumptions register, risks register, and ADR log from Part V were quietly becoming.

The real artifact is not the code. It is the accumulated decision intelligence that explains why the code is the way it is.

6.3

Orchestrator Evolution

Senior engineers do not start with multi-agent. They start with a single orchestrator, because orchestration complexity explodes. The memory pipeline grows the same way.

V1 / one orchestrator
A single flow: capture, evaluate, store, retrieve, compose. Few specialized workers. Ship this first.
V2 / specialized agents
Add an extraction agent, an evaluation agent, a reflection agent, a conflict-resolution agent under one orchestrator.
V3 / dynamic routing
Invoke agents only when needed. Most messages need cheap capture, few need heavy reflection.

The most commonly missing component across all three versions is reflection. After every major step, ask what happened, what worked, what failed, what surprised us, what should be remembered, and store the answer. That is how systems improve themselves rather than merely run.

Carry into the architecture

A staged orchestration plan (V1 single, V2 specialized, V3 dynamic) plus an explicit reflection step that writes to learning memory.

How high-maturity organizations actually start

Watch how a serious software organization plans, and you notice it does not start with architecture. It starts with classification, requirements, risk, traceability, verification, and governance. Only then does implementation begin. That order is very different from the typical AI workflow that jumps straight to a vector database and code.

The deliverable
7.1

Plan Before Code: Nine Phases

The implementation plan does not begin with Postgres, pgvector, Redis. It begins with mission and classification, and it earns its way to a stack.

Phase 0 / Mission definition

What problem does memory solve? Mission: improve answer quality through personalization. Success: the user repeats themselves less. Constraint: no memory leakage. This is the north star.

Phase 1 / Memory classification

Not all memory deserves the same rigor, so classify it and apply different rules per tier.

TierKindExample
1User preferences"Short answers"
2Project knowledge"SBL pricing"
3Critical informationPayment details, PII, credentials
4System knowledgeAgent lessons, reflections

Phase 2 / Requirements mapping matrix

Before coding, map each requirement to how it will be verified.

RequirementVerification
Memory survives restartIntegration test
Memory retrieval under 100msLoad test
User can delete memoryAcceptance test
No cross-user leakageSecurity test

Phase 3 / Traceability

In plain terms: for anything the system believes or does, you can follow the trail back to where it came from. You should be able to answer "why did the system think this" at any moment.

What you actually trace, with examples:

  • A belief back to its source. "Prefers short answers" traces to conversation 42, message 7, on June 3. If it is wrong, you can see exactly where it came from.
  • An answer back to the memories it used. This reply loaded memories 118, 204, 351, so you can show the user why it was personalized that way.
  • A memory back through its changes. This fact was created low-confidence, updated twice, merged once, and you can replay each step.
  • A deletion back to who ordered it. Memory 351 was deleted on the user's request on June 18, logged and irreversible.

All of this rides on the source field the record has carried since Level 2, plus an append-only log of every write, read, and delete. Trace user statement, to extraction, to record, to retrieval, to response, in both directions.

Phase 4 / Failure analysis before coding

Ask, before writing code, what happens when extraction fails, retrieval fails, the embedding service is down, the wrong memory is retrieved, a memory is deleted. Answer each with a fallback.

Phase 5 / Verification strategy

Where most AI systems are weak. Unit tests that extract_memory() works. Integration tests that write, retrieve, delete works. Adversarial tests that user A's memory never leaks to user B's query. Regression tests on known retrieval cases.

Phase 6 / Measurement repository

Store retrieval precision, retrieval recall, correction rate, memory utilization, latency, and cost, so future decisions stand on data instead of opinion.

Phase 7 / Architecture

Only now, and it is easy, because Parts I to VI already built it: capture, evaluation, store, retrieval, ranking, context builder, wrapped in the production planes.

Phase 8 / Build plan

7.4

From Design to Code

The design is done. Here is how you actually build it, by driving an AI coding agent through the decision loop from Part VI, one sprint at a time.

The build order

Follow the nine-phase plan's last step: schema, extraction, retrieval, ranking, context builder, observability, governance, reflection. Each sprint ships one working slice and is gated by a test before the next begins. You are never building the whole system at once.

Start with the schema

Everything else hangs off the record. This is the first thing to hand the agent.

create extension if not exists vector;

create table memories (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null,
  type          text check (type in ('episodic','semantic','procedural')),
  content       text not null,
  embedding     vector(1536),
  importance    int,            -- set by the evaluator
  confidence    real,           -- how sure we are it is true
  source        jsonb,          -- provenance: conversation, message, time
  weight        real default 1.0,
  reinforcement int  default 0,
  archived      boolean default false,
  created_at    timestamptz default now(),
  updated_at    timestamptz default now()
);

create index on memories using ivfflat (embedding vector_cosine_ops);
alter table memories enable row level security;   -- invariant 1

A repository the agent can fill in

memory-system/
  api/        gateway, auth, routing
  capture/    extractor + evaluator (the write gate)
  store/      schema, write service
  retrieve/   retriever + ranking
  context/    composer
  jobs/       decay, reflection
  evals/      golden set + regression tests
  adr/        decision records

Driving the AI coding agent

Do not ask the agent to "build a memory system." Give it the design, one goal, and a clear finish line, then run the loop: it plans and implements, you observe through tests and evals, you feed back, it moves to the next sprint. A single turn looks like this.

Context   This architecture, and the four invariants. Never break them.
Goal      Sprint 3 only: build retrieval (vector + keyword), with ranking.
Build     Plan the files, implement them, write the golden-set eval.
Done when The retrieval eval passes at 90% precision and no test
          retrieves another user's memory.

The agent writes the code, the eval tells you the truth, and every decision it makes gets logged into the adr/ folder so the next sprint inherits the reasoning. This is the decision loop in practice: the codebase is the output, but the accumulated decisions are the asset.

What you do now

Open the schema, scaffold the repo, point a coding agent at Sprint 1 with the invariants pinned, and let the loop run. You are no longer reading about a memory system. You are building one.
